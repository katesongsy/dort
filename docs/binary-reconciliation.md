# Session snapshots and binary metadata reconciliation

Tools reconciliation connects explicit provider-inspection snapshots to the [pure package planner](tools-planning.md). It does not install packages, execute discovered candidates, infer ownership, create receipts/trust or change any lifecycle journal. End-user usage is in [snapshot reconciliation](user/commands.md#snapshot-reconciliation).

## Collection and scope selection

`services::reconciliation::Snapshot` contains an immutable ID and shared metadata-only inspection report. Sharing uses `Arc`, not cloned approvals or raw provider payloads. Sessions retain at most 16 snapshots and 65,536 total installation records. Snapshots are not persisted or deserialized as trust. Forgetting one removes session metadata, not a package or any earlier provider side effect; dropping references is not secure erasure.

The TUI assigns stable session IDs (`s1`, `s2`, …) after individually approved inspections. Selecting/browsing/forgetting snapshots never queries providers. A fresh query always needs a new real core preview and literal confirmation. If capacity is already exhausted, a new preview is withheld before approval. A result that would exceed the remaining record budget is explicitly reported as executed but not stored; it is not silently substituted for an existing snapshot or automatically retried.

The CLI collection phase accepts repeated strict typed JSON scope requests with explicit ID, provider, executable and child search directories, plus npm binding fields when applicable. Unknown fields, duplicate IDs and invalid bindings are rejected before provider execution. These are request descriptors, not serialized approvals: each is reconstructed into a real fixed-operation core preview and independently approved. Human execution asks whether to run each identified scope (`y/N`); explicit `--yes` is the CLI automation alternative. `--dry-run` returns all preview/context descriptions without provider execution or binary lookup. Earlier separately approved scopes may already have run if a later scope is declined or reconciliation fails; nothing is automatically undone.

Reconciliation binds **each selected tool explicitly to a snapshot ID**. No binding means not observed, even when exactly one matching provider exists. There is no implicit provider/home/prefix merge, fallback to another catalog, alias resolution or ownership inference. Multiple same-provider scopes remain distinct. UI choices filter by declared provider, but the core still reports wrong scopes defensively. Failed observations never become healthy empty catalogs.

## Manifest and profile provenance

A standalone reconciliation request supplies an absolute manifest, explicit tool-search directories and temporary profile additions. Registration, the selected file repository and local variable values are not loaded. Manifest/base/default/platform/requested profile resolution is explicit. The bounded no-follow owned-regular-file manifest service parses declarations; source-bearing parse/read errors are replaced with static diagnostics. A prepared request records the manifest fingerprint/hash and rechecks it before analysis, rather than silently using changed declarations.

npm inspection reports privately retain the source manifest fingerprint/hash for the session, skipped by serialization. Selecting an npm snapshot for another path or changed manifest is refused; a matching runtime ID alone cannot rebind globals to a different declaration scope. A fresh approved snapshot is needed. This check does not prove that a Node/prefix is provider-owned, establish snapshot freshness for external package databases or grant installation authority. The pure planner retains its separate necessary runtime-candidate scope checks. Eligible rows can include [non-executable command descriptions](install-command-previews.md); inspection approval and `--yes` never execute those descriptions.

## Metadata-only candidate observation

`dort_core::tools::binaries` observes only selected declared bare binary names in **separately supplied tool-search directories**. It never discovers process PATH, reuses a provider's child search path, launches `--version`, follows a candidate symlink or reads/hashes candidate contents.

All access uses the existing descriptor-relative no-follow observation helpers. Directories are checked before probing; each entry is checked twice, and directories are revalidated afterward. Leaf fingerprints and literal UTF-8 symlink targets are inspectable metadata. Symlinked parents/directories, missing/unreadable directories, changed scope/entry metadata and invalid link targets make the relevant observation unavailable, not healthy empty. No automatic canonicalization or unsafe path-based fallback is used. In particular, a system `/bin` symlink is not silently traversed; callers must choose physical directories.

All occupied names remain unattributed paths, including nonexecutable regular files, directories, special files, hard links and dangling symlinks. Recording their kind is not approval to open, execute, adopt or overwrite them. This prevents a nonexecutable/special occupant from being misreported as safe binary absence. A complete empty lookup means absence only in the explicit directories, not global absence, version satisfaction, executable readiness or ownership. Unavailable partial scopes cannot justify absence even when other directories were successfully inspected.

Requests allow at most 32 distinct directories, 4,096 selected tools and 32,768 tool/directory probes. Directory strings are absolute UTF-8 without dot/NUL/PATH-separator components, bounded to 4,096 bytes and 64 components. Names sharing a binary reuse probe metadata, but reported scope remains bounded. These are count/path bounds, not a hard wall-clock filesystem deadline or isolation against same-user races. Metadata can change after the snapshot. The separate [exact mise/npm installers](tool-installation.md) independently reconstruct approval and revalidate fresh observations under the writer lock; they do not execute these rows or infer ownership.

## Frontend data flow and presentation

The CLI explicitly collects approved scopes, then `Prepared::reconcile` rereads the manifest, validates chosen snapshot bindings, observes binary metadata and calls the pure planner. This method itself never executes or refreshes a provider. Final JSON contains snapshots plus the analysis scope, explicit bindings, binary metadata and package plan. Exit 1 denotes an unavailable requested provider or binary observation; otherwise blocked package plans return 4, invalid requests/approval/provenance return 2, and a completed package analysis returns 0. Package no-change is not tool readiness, even on exit 0.

The TUI uses the existing single owned joined worker for loading declarations and reconciliation, independently of query approval. Inputs and explicit per-tool choices retain their drafts; unbound tools remain unknown. Selected-snapshot scope is inspectable before calculation. Results are typed viewport-only rows; selected full metadata uses bounded visible wrapping with usize scrolling, rather than truncating long reports at a u16 offset. Printable input shortcuts, compact/wide caret/focus styling, below-floor guards and late-result navigation behavior follow existing workbench rules. A failed declaration-load retry reloads metadata, never a provider query. Forgetting snapshots invalidates cached analysis, never silently reassigns bindings. Eligible missing exact mise/npm rows additionally offer a dedicated process-free install review; one activation approves its independently constructed core preview. `--install-tool` is the explicit CLI opt-in after collection/reconciliation. Install outcomes invalidate cached analysis without replacing historical snapshots.

Reports remain outside generic write receipts/journals and contain no candidate body, raw provider stderr/stdout, parser source lines or configuration contents. Metadata is escaped for terminal rendering. Package no-ops/proposals, binary observations and blockers remain separate, so no color or aggregate label asserts a usable/owned installed tool.

## Validation boundary

Core fixtures use disposable canonical homes and test explicit empty/unavailable scopes, all occupied file kinds, symlinks, unsafe identities and no candidate execution/content disclosure. CLI/TUI fixtures cover multiple scopes and explicit bindings, no automatic merge/refresh, preview-only and approval modes, missing/failed observations, changed/different npm declarations, retained drafts, snapshot limits, literal shortcuts and compact/wide caret/selection behavior. PTY checks exercise collection, selection/forgetting, binding/results and separately confirmed CLI scopes with terminal restoration. They require no installed providers/Node and do not establish real-provider compatibility, OS sandboxing, atomic filesystem snapshots or unfamiliar-user intuitiveness. See [validation methods](validation.md).
