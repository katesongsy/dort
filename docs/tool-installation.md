# Bounded Tools installation and attempt metadata

The normal [declared-tool workflow](declared-tools.md) prepares eligible absent rows and reviews their core capabilities as one immutable set, then executes serially under the application lock and stops on failure. It preserves the per-package contracts below, reports partial effects/not-started tools, and performs no rollback or silent upgrade. The public entry point is Install missing; internal row capabilities remain separate opaque approvals.

Installation review, necessary Tool settings, history, closure and outcomes follow the [shared interaction contracts](tui-interactions.md). Enter opens a selected tool/record; named actions prepare exact reviews. Closure asks for provider/scope fields only when the original record cannot supply them, with F4 provider choice and retained drafts. Human-readable reviews show all required scope facts without alternate JSON/F3 modes. Compact reviews keep execution/no-rollback warnings visible. Real approvals, unresolved guards and joined-worker supervision remain independent of navigation.

`tools::install` is a separate opaque core capability, not an executor for `tools::install_preview` descriptions. The internal `services::installation` adapter reconstructs requests from the current check's exact associations and metadata. CLI `tools install-missing` and the same TUI action use one combined reviewed set, with no manual snapshot or binding step. A separate Homebrew capability installs a missing canonical core formula at provider-current default/latest policy on macOS, Linux and WSL. See the [user installation guidance](user/commands.md#installation-safety).

## Scope and approval

One observed missing npm exact semver package or supported canonical core formula, an independently missing declared binary and clear prerequisites can be reviewed. The repository must be registered. Profiles include persistent selections and explicit additions; the adapter refuses a changed reconciliation profile scope instead of silently expanding it. npm and Homebrew use exact internal target/prerequisite associations across independently observed scopes (npm additionally requires its declared runtime). Necessary prerequisite closure is taken from declared dependencies, never inferred from ownership. Catalogs are not merged. Existing, conflicting, ambiguous, unobserved, unmanaged or blocked states do not authorize installation.

Preparation is process-free. It binds the bounded stable manifest, registration/profile configuration, host context, explicit regular executable and separate no-follow declared-name lookup directories. No candidate is executed. Public review metadata includes the selected package/version, repository/profiles, executable, provider child PATH, independent binary lookup scope, fixed arguments and deadline. Only consuming the real in-memory preview creates approval. Neither a stored attempt nor JSON metadata can recreate it.

One frontend confirmation covers fresh inspection, conditional installation and post-inspection. Execution holds the application writer lock, checks existing file-journal write guards and unresolved Tools attempts before querying, independently revalidates all bindings, and rebuilds eligibility from fresh fixed provider queries and binary metadata. npm and Homebrew revalidate their program/source/directory identities before and after each required query; read queries may be brew or npm, never another provider's installer. A newly satisfied package claim is a no-op with no installer or attempt; other conflicts or unavailable observations refuse. Intent/head/source guards are checked again immediately before spawn. An attempt invalidates the previous check's installation authority. Check installed must gather newly approved observations before another install review. Earlier results are not a fallback and recomputing old metadata cannot re-enable installation. Internal explicit associations remain tied to the exact newly reviewed scopes.

## Fixed process and worker contract

### npm runtime, prefix and fixed protocol

npm requires the declared runtime ID and the exact physical Node/npm CLI/global-prefix binding from a matching unchanged session manifest observation. The pure planner must still find the bound Node as the sole runtime candidate, with a satisfied runtime package claim and clear prerequisite rows. Each necessary explicit catalog is freshly queried under the writer lock. Neither closure nor inspection manufactures runtime satisfaction. Preparation does not query providers or execute Node/npm version/config commands.

The global prefix must be a physical owned directory strictly inside HOME, or absent descendants of safe owned parents there; its absolute ancestor chain is bounded to 32 entries. Required parents (prefix, `lib/node_modules`, any selected scoped-package parent, `bin`, `share/man` and ancestors) must be directories without group/world write access. Source snapshots bind their identities and the trusted programs plus independent no-follow tool-search directories. Node and npm CLI cannot lie in the selected prefix's native write roots. Approved missing parents are created descriptor-relative and synced only after durable intent; new identities are pinned before spawn. The initial scope/source budget applies to the durable intent; expanded in-memory fingerprints after approved parent creation do not re-encode or enlarge that immutable record. Native npm writes are trusted-program hardening, not isolation against a malicious same-user path race.

Node executes the selected CLI directly, never the npm wrapper:

```text
NODE NPM_CLI install --global --prefix PREFIX --ignore-scripts \
  --audit=false --fund=false --update-notifier=false --logs-max=0 \
  --loglevel=silent --registry=https://registry.npmjs.org/ \
  --userconfig=/dev/null --globalconfig=/dev/null PACKAGE@EXACT
```

The same cleared HOME/XDG/PATH, fixed locale, `/` and null-stdin boundary applies, with no provider-controlled environment additions. No inherited terminal/credential environment, arbitrary argv, private auth or weaker fallback is provided. Trusted builtin npm configuration and dependency behavior remain in scope: a fixed registry is not strict endpoint isolation or a promise that npm cannot read HOME.

Native dependency-tree writes and bin/man links are approved effects. They can expose commands immediately if prefix/bin is on PATH; npm is **not activation-free**. Dort does not edit PATH or runtime configuration. Disabling lifecycle scripts does not establish package usability; effects are not atomic and other prefix entries are not isolated. There is no intentional other-top-level upgrade, force, uninstall or rollback request.

### Homebrew core formula protocol

`tools::install::brew` supports only unqualified canonical core formula names on macOS, Linux and WSL, with omitted or `latest` version policy. Versioned names are identities, not exact patch pins. Qualified tap names retain the pure planner's identity rules and are not executable by this slice. Casks, aliases/renames, disabled/unknown formulae, HEAD, arbitrary options/URLs/files, services and privileged layouts refuse.

Preparation is process-free. An inspectable prefix hint derives only from the selected physical `REPOSITORY/bin/brew` path; supported repository layouts are `PREFIX` or `PREFIX/Homebrew`, with `PREFIX/Cellar`. The frontend derives the expected physical prefix from the selected program; fresh layout mismatches refuse installation. Homebrew's folders must already exist as real directories writable by the caller: Cellar, bin, etc, include, lib, opt, sbin, share, var, var/homebrew, and repository/Library. World-writable folders and folders writable by a group the caller is not in are refused. Homebrew's usual admin-group ownership is accepted when that group is one of the caller's groups; other members of those groups can still change the prefix. A root-owned prefix such as `/usr/local` must stay owner-writable. No group inference beyond the caller's own groups, directory creation or sudo fallback is used. Refusals name the folder and problem: missing or not a real folder, writable by everyone, writable by a foreign group, owned by another account or an unsafe parent. Parent identities are bound; schema-3 metadata deduplicates ancestor chains without discarding identities. This does not isolate a trusted native program's writes or nested prefix entries against same-user races.

One approval covers fixed bounded `brew help install`, `--prefix`, `--repository`, `--cellar`, `info --json=v2 --formula homebrew/core/FORMULA`, necessary installed catalogs and post-observation. Normal inspection collection does not gain these commands. Help must advertise `--formula`, `--no-ask`, `--skip-post-install` and the install-upgrade/dependent/cleanup guards. Layout probes must return one matching absolute path; only the explicitly expected physical paths are observed/revalidated. Unmatched provider path strings are never passed to filesystem observation or copied into errors. Target JSON is whitelisted to canonical name/full-name, core tap, availability and version/install metadata; aliases/renames and contradictory catalog claims refuse. Help/JSON bodies and descriptions never enter reports or attempts. Advertised controls are hardening, not an installed-provider compatibility or malicious-program guarantee.

```text
brew install --formula --no-ask --skip-post-install homebrew/core/FORMULA
```

The cleared HOME/XDG/PATH, locale, `/` and null-stdin contract applies with `HOMEBREW_NO_AUTO_UPDATE`, `HOMEBREW_NO_ANALYTICS`, `HOMEBREW_NO_ENV_HINTS`, `HOMEBREW_NO_INSTALL_UPGRADE`, `HOMEBREW_NO_INSTALLED_DEPENDENTS_CHECK` and `HOMEBREW_NO_INSTALL_CLEANUP`. No arbitrary environment or weaker fallback is supplied. Formula/build/resource/dependency code **can execute**, dependencies can install/upgrade, and native links can expose commands on PATH. Skip-post-install is not a ban on build code; this is not bottle-only, exact-pinned, atomic, isolated or a usability guarantee. Trusted Homebrew can download and maintain native metadata/caches; no strict endpoint or HOME-access isolation is promised. Dort does not request link/services/cleanup/upgrade/reinstall/pin/tap, manager installation/update or PATH/runtime edits.

### Shared worker and observation

Installers have a displayed ten-minute deadline; inventory queries retain their independent ten-second deadline and bounded parser inputs. Concurrent nonblocking fair stdout/stderr drains discard installer bytes, including successful output; only typed phases and outcomes leave the runner. Timeout/pipe failure terminates the owned process group and joins/reaps it, possibly after partial effects. The existing single owned joined worker and single input thread remain unchanged. Quit/Ctrl-C waits for approved work; no cooperative cancellation, detached workers or automatic rollback is provided. Progress uses separate typed install events, not fabricated file-journal checkpoints.

Post-inspection is attempted after process failure as well as success. A changed source/executable prevents re-executing the changed provider. Process outcome, package claim and binary metadata availability remain separate. Homebrew uses `provider_current_present`, never `exact_present`, with whitelisted observed versions; this is not a readiness claim. Output persistence failure is an unresolved attempt, never implied success. Reports do not claim binary readiness.

## Separate durable attempt store

`STATE/tools-attempts/<64-hex-id>/` is independent of file transactions and Recovery. Descriptor-relative no-follow private helpers create and sync immutable checksummed records:

- `intent.json`: schema 2 for npm or schema 3 for Homebrew, attempt ID, requested scope and private source fingerprints/hashes; durable before installer/prefix mutation. npm adds runtime/CLI/prefix and catalog/parent/program bindings. Homebrew adds provider-current policy, native layout, advertised probe facts and deduplicated parent/program identities.
- `outcome.json`: observed typed process/package/binary outcome bound to the exact intent artifact.
- `close-NNNN.json`: explicit fresh-inspection closure bound to the unchanged census/head of all earlier artifacts; append-only, never repair/overwrite an earlier record.

Envelopes validate the checksum of the exact raw payload string before typed parsing. Outcomes bind the full exact intent artifact; closures bind the census/head including earlier artifact bytes. npm outcomes/closures use schema 2 and Homebrew uses schema 3. npm outcomes accept exact presence; Homebrew outcomes accept provider-current presence. Only these two provider schemas are supported. Supported payload bytes are never re-encoded.

Records contain metadata, not raw output, manifest/configuration bodies, variable values, credentials, backups or persisted trust. There is no file-journal format change. Bounds are 256 attempts, 32 files per attempt and 64 KiB per record; exhausted or unsafe storage is refused, never silently evicted or followed through symlinks. File and directory sync establish the ordinary durability protocol; process-exit tests do not prove power-loss safety.

Missing/malformed intent, incomplete outcome, changed artifacts or invalid closure leave an unresolved attempt. Only subsequent Tools installations are blocked; unrelated file workflows are not blocked by this store. Startup never replays, cleans up, resumes or rolls back an installation.

## Derived outcome summaries and fresh review

`tools::install::outcomes` interprets typed metadata without I/O, clocks, provider queries or execution authority. Public installation reports and attempt listings add a derived `summary`: textual status/explanation, independent process/package/binary facts, binary uncertainty, an explicit next-step hint and `readiness_verified: false`. Complete process failure remains failure even when post-inspection reports the package present. A completed process with an absent, conflicting or unavailable package is not reported as an installed match. Installer unavailability, unverified process observation (pipe/wait failure) and elapsed requested deadline are distinguished from a known unsuccessful native exit. Exact/current matches describe package claims only; binary candidates are not executed and establish neither readiness nor ownership. Unresolved records take precedence over an older outcome; explicit historical closure is acknowledgement, not install success, repair or readiness proof.

Summary serialization is confined to public borrowed report views. The private intent, completed-outcome and closure payloads retain schemas 2 and 3, exact raw checksums/artifact hashes and historical heads; no derived summary is stored or used as approval. There is no environment receipt, persisted trust, ownership model or new retry capability. Complete failed attempts remain readable historical outcomes, not unresolved merely because the native process failed; write guards still reject incomplete/malformed/changed state.

Results explain whether to check installed again, resolve a blocker or inspect an unresolved record. They never reuse installer input or approval. Check installed prepares fresh query approval, then Install missing constructs a new exact eligible set. Pending attempts still block writes until guarded explicit closure succeeds; checking does not close or replay them. Preview-only, floor/shrink, source and joined-worker guards remain intact in both interfaces.

## Explicit inspection and closure

Both frontends list all-repository attempt metadata, distinguish unavailable storage from an empty list, expose full IDs/scope/outcomes, and offer a process-free closure preview. A valid original scope requires its original executable/home/PATH; damaged or missing scope requires an explicit provider and trusted executable/child PATH, with Node/npm CLI/prefix for npm or the original prefix for Homebrew. Fallback runtime labels describe historical probes only, not declarations or satisfaction. Closure is historical metadata handling, not a current manifest operation.

One deliberate activation acquires the writer lock, checks unchanged head/host/executable bindings, runs a fresh fixed query for the historical provider scope, requires a complete observation and appends a head-bound closure. Unavailable queries do not close anything. A closure never retries an installer, repairs packages, verifies readiness or asserts that a damaged record was successful. Editing an earlier artifact invalidates the closure and makes the attempt unresolved again. Retry always prepares a fresh preview; no approval is replayed. File-journal problems do not prevent this separate metadata-only closure workflow. Current manifest availability or unchanged declarations are not required for historical closure; trusted npm CLI identity is checked as well as Node. Homebrew closure also brackets a fixed `--prefix` query with prefix/program identity checks and requires the original prefix before its complete installed catalog; no current declaration or runtime proof is fabricated.

## Validation boundaries

Disposable fake-provider fixtures cover fixed arguments/environment, output discard, source/profile/registration/executable drift, scope and prerequisite refusal, intent/outcome failure boundaries, independent file guards, unresolved-only Tools blocking, malformed/changed attempt closure, process exits, deadlines and descendant-held pipes. CLI, typed TUI/cell/caret and PTY checks exercise one-activation review, progress, joined exit, compact layouts and explicit closure. No workstation provider install, network compatibility, unfamiliar-user usability or power-loss guarantee follows from these checks. See [validation methods](validation.md).
