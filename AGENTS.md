# Working on Dort

These repository instructions apply to all files unless a more specific instruction overrides them.

## Mandatory TUI design contract

Before changing TUI behavior or presentation, read [the design system](docs/design-system.md) and [interaction contracts](docs/tui-interactions.md). These tracked pages are the authoritative standards; ignored proposals are not required build/agent inputs. Identify the shared components/semantic roles you will reuse before editing. All shared visual components belong in the Rust module folder `crates/dort/src/tui/components/` (not a separate Cargo package); page/workflow controllers and approval ownership stay outside. Keep colors, emphasis, semantic glyphs and motion in that shared foundation, not page-specific implementations. Use one foreground action strip, distinct input/fact/selection/feedback styles and honest progress; preserve every approval/privacy/joined-worker invariant. New component semantics, exceptions or standard changes require explicit operator review. Do not silently remap unrelated workflow keys during a visual migration. The current shell uses groups-first Places at every width, a wide destination rail, Ctrl-K global tasks, F2 contextual More, F3 metadata and Ctrl-N Create/attach. Form traversal excludes action strips; explicit readers own arrows/paging rather than hidden rows.

Run the style checker/self-tests, actual-component/backend tests and normal workspace/docs/terminal gates. Do not weaken checks, add exceptions or regenerate visual expectations merely to make tests pass; inspect and explain differences, and obtain review for changed visual baselines. Report reused components, validation actually run and remaining deviations. Automated passes and an AI-updated snapshot are not unfamiliar-user or human visual approval. Keep temporary migration worklists/evidence in ignored specs/temp; maintain only durable rules and current behavior in tracked docs.

Preserve the shared [workbench interaction contracts](docs/tui-interactions.md): workflow forms/reviews/results are navigable pages, short choices/help/final gates are explicit dimmed dialogs, field/row traversal never includes footer buttons, and Enter invokes the contextual primary action. Keep drafts and opaque previews when menus are merely opened/dismissed; discard approvals on actual navigation. Dialog/busy navigation must explain its restriction, not silently ignore input. Keep trusted decoration separate from escaped metadata, foreground-only caret/hits, compact direct actions and existing approval/privacy/joined-worker guards. Automated tests do not replace unfamiliar-user usability review.

## Scope and current capabilities

- Read [README.md](README.md) and [ARCHITECTURE.md](ARCHITECTURE.md) before changing behaviour.
- Dort is a Rust workspace: `crates/dort-core` owns UI-independent services; `crates/dort` owns the Clap CLI, Ratatui workbench and presentation.
- The experimental CLI exposes approved local init/attach, regular-file adoption, link apply, unmanage and guarded recovery. Keep discovery/checks/plans/status/history/Git inspection read-only and provider-free. The approved Tools provider-inspection workflow is separate: fixed queries require a deliberate risk-disclosing preview and single-use in-memory approval, explicit trusted paths and bounded/redacted process handling. CLI `tools inspect`, the separately approved collection phase of `tools reconcile`, and the Tools TUI are the inspection-only provider paths; the separately approved mise/npm/Homebrew/APT installation and attempt closure capabilities are described below. Dry-run previews never execute. TUI/interactive CLI use a simple explicit confirmation action, never a typed phrase (CLI automation may use --yes). Preserve explicit npm declared-runtime/Node/CLI/prefix binding, unavailable-versus-empty results, retained drafts, fresh review on retry, below-floor/entry-dry-run guards and shrink-cleared confirmation. Inspection defaults must remain metadata-only with captured application-boundary PATH inputs: no provider/launcher/version/config-query probing. Prepare every selected real preview before one collection confirmation; preserve Advanced overrides and leave unresolved npm bindings explicit. Test discovery with synthetic PATH/layout fixtures, never operator package managers. Session snapshots are bounded metadata, not trust/receipts; forgetting them never uninstalls or undoes provider effects. Reconciliation itself never queries providers: bind every tool explicitly to a chosen snapshot, keep unbound/failed/ambiguous observations distinct, and observe only declared names in separately supplied tool-search directories with no-follow metadata helpers. Never execute candidates, infer provider ownership from names or reuse provider child PATH as tool lookup scope. npm snapshots must retain matching session-only manifest provenance; changed/different declarations require fresh inspection, never rebind/replay silently. Package no-op/proposal results and install argv/control descriptions are metadata, not tool readiness or installation authority. Never dispatch `install_preview` data: mise/npm/Homebrew installation uses separate `tools::install` previews/approvals, not those serialized descriptions. Preserve no-command behavior for satisfied/blocked/ambiguous rows, explicit unresolved native defaults, npm ignore-scripts caveats, Homebrew dependency-upgrade risks and APT's separate explicit privileged-program/root-risk review (never an invented sudo handoff). These descriptions do not authorize installation or persisted trust/receipts. Do not broaden provider execution/installation beyond the approved exact mise/npm and bounded provider-current Homebrew contracts, or add automatic execution, cloning/sync, Git staging/commit/push or unrelated writes.
- Executable package writes are limited to one observed missing exact mise version, exact npm registry package or canonical Homebrew core formula/literal Ubuntu APT package at provider-current default/latest policy in a registered repository with explicit profiles and snapshot/dependency bindings. Preserve process-free review, one activation, fresh writer-lock/source/manifest/profile/executable/binary validation, file-journal guards, fixed provider-specific arguments, output discard, the provider-specific requested ten-minute deadline/supervision contract and joined quit. Mise keeps its same-snapshot, inactive-only contract. npm requires fresh explicitly bound target/runtime/prerequisite catalogs, sole selected Node candidate, unchanged manifest provenance, physical trusted Node/CLI and an owned no-follow prefix strictly inside HOME. Refuse Node/CLI inside npm's native write roots; bind prefix parents, create only approved absent parents after durable intent and retain their identities. Fixed npm controls disable lifecycle scripts, audit/fund/notifier and user/global npm config; native dependencies and bin/man links may expose commands on PATH. No sandbox, strict endpoint isolation, usability, atomicity or other-prefix-entry isolation guarantee follows. Homebrew accepts only unqualified canonical core formula names on macOS, never aliases/taps/casks/HEAD or exact patch pins. Review includes fixed help/layout/formula probes; require advertised fixed install controls and matching physical repository/prefix/Cellar, existing owned native write roots (safe root-owned non-writable prefix parent allowed), explicit necessary cross-catalog prerequisites and independent no-follow binary directories. Keep Advanced prefix and damaged-scope provider drafts retained; never silently rebind. Formula/build/dependency code CAN EXECUTE, dependency installs/upgrades and native command links are disclosed effects; skip-post-install is not a sandbox or bottle-only assurance. No PATH/runtime-config edits, private auth, broader privilege than the bounded noninteractive APT contract below, force, intentional other-top-level upgrades, uninstall, rollback or persisted trust.
- Persist private immutable checksummed intent before installer/prefix mutation and typed observed outcome afterward in separate Tools attempt storage. npm uses explicit schema-2 metadata; Homebrew uses schema 3 with provider-current policy, layout/probe/source bindings and non-exact observed versions. Ubuntu APT uses schema 4 with selected dpkg/apt-cache/apt-get/sudo, candidate/supervision/source metadata and provider-current outcomes. Preserve schema-1/2/3 raw payloads and heads. APT alone uses trusted sudo -n -T 600 supervision with explicit policy permission: no password capture, sudo validation/cache manipulation, policy changes, untimed fallback or user SIGKILL-group assumption. On overdue supervision signal sudo with catchable TERM and keep waiting joined, with honest metadata progress; no strict OS deadline or proof of root-descendant termination. Root scripts/hooks, dependency upgrades, services and system/config/data/live-link effects are explicit risks. Closure is dpkg-only and proves neither termination nor repair. Fake-program tests never establish real root containment; real-root/provider validation needs separate disposable-environment approval. Preserve schema-1 mise and schema-2 npm bytes, raw-payload checksums, exact intent artifact hashes and head-bound closures without migration. No file-journal/schema change or package backup is authorized. Shared derived outcome summaries belong only in public report views, never private intent/outcome/closure payloads or approval ownership. Preserve process failure even with package presence, unavailable-vs-empty binary/package facts and closure-not-success semantics. Fresh-review entry is navigation/metadata discovery only: retain current scope/drafts, mark old IDs stale, never auto-query/bind/replay, and require new inventory approvals, explicit bindings and a fresh install review; unresolved guards remain in force. Unresolved attempts block only Tools installs; both frontends must inspect metadata and offer fresh-query/head-bound historical closure, including damaged-scope provider/Node/CLI/prefix inputs without a current-manifest or runtime-satisfaction claim. Never replay on startup/retry or refresh/rebind historical snapshots; invalidate reconciliation and require fresh explicit bindings after an install. Tests use fake providers/canonical disposable homes only, never real package managers or credentials.
- Tools → Add tool declaration and CLI `tools declare` add one validated desired Tool to an already registered repository. Keep this manifest-only: no provider/candidate execution, installed-binary adoption, ownership claim, update or removal. Identical typed declarations are no-ops; conflicting IDs are refused. Preserve unrelated TOML/comments, opaque preview ownership, lock/fresh revalidation, private durable backups and separate checksummed schema-5 intents. Incomplete/malformed transactions block all writers; explicit guarded rollback must refuse later edits. Keep schemas 1–4 compatible, raw manifest bytes out of reports/Debug/journal metadata, and npm snapshots stale after manifest changes. Maintain TUI/CLI declaration and Recovery parity with simple confirmation actions, retained drafts, dry-run/shrink guards and disposable failure-boundary/process-exit tests.
- The current TUI exposes Overview, searchable Actions/help, session repository/profile selection, guided create/attach, Files discovery/adoption/apply/unmanage, structural Checks with host Diagnostics/About, searchable all-repository Recovery with contextual action hints, explicit Tools provider inspection, and read-only Git status/diff with separately confirmed patch viewing; it remains experimental. The accepted v0.1 boundary is **TUI-first, polished and complete for every supported CLI workflow**. The interim parity/UX roadmap belongs in ignored `specs/`, not tracked documentation. Before release, complete usability review and exact-candidate validation. Preserve keyboard-only compact/wide navigation, textual (not color-only) state, retained drafts and inspectable escaped metadata. Keep typed Files/review presentation separate from opaque approval ownership; cell-style/caret/focus assertions supplement text and PTY checks. Enter on a discovered row inspects it; candidate adoption is a separate action. Automated state/view/PTY checks do not establish unfamiliar-user intuitiveness. Keep doctor metadata shared across frontends, diagnostics content-free, and unavailable observations distinct from healthy empty results. Recovery eligibility hints never replace core previews; failed-write retries must not retain/replay approvals. No supported task may be completed by a CLI handoff; JSON/automatic-approval flags remain CLI automation concerns. Do not add provider execution or change journal/schema/security/cancellation contracts without explicit agreement. The TUI patch flow requires a concise content warning and one explicit view action per view, not a typed phrase; do not broaden it into automatic content viewing.
- Keep existing uncommitted work intact. Do not commit, push, tag or release unless requested.

## UX priorities

- Make supported tasks as easy as possible for users. Prefer straightforward defaults, clear actions and short, useful explanations.
- Do not overdo defensive phrasing, warnings, confirmation layers or speculative safety features. Keep necessary safeguards in the implementation without making routine workflows cumbersome.
- Never require users to type literal words, phrases or IDs to confirm an action. Use a clear button, key activation or simple CLI confirmation instead. Show the action and its scope; bind approval internally to the exact preview/selection.
- These priorities supersede earlier typed-confirmation UX requirements. When revising existing flows, align their behavior, tests and maintained documentation with this policy.

## Rust workflow

- Use the pinned Rust 1.99.1 toolchain, edition 2024 and committed `Cargo.lock`.
- Prefer existing dependencies. Make lockfile changes deliberately, then validate with `--locked`.
- Keep domain policy out of CLI handlers. The pure planner must stay free of filesystem I/O, clocks and randomness.
- Use explicit `HostContext` inputs; only the application boundary discovers environment/platform values.
- Run from the repository root:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked -- --test-threads=1
cargo build --workspace --locked
python3 scripts/check-docs.py --self-test
python3 scripts/check-docs.py
python3 scripts/check-tui-style.py --self-test
python3 scripts/check-tui-style.py
python3 scripts/test-terminal.py
python3 scripts/test-cross-device-macos.py --self-test
python3 scripts/release.py --self-test
python3 scripts/check-crates.py --self-test
python3 scripts/check-crates.py
cargo package --workspace --locked
python3 scripts/check-crates.py --archives
git diff --check
```

Run independent Rust test cases serially (`--test-threads=1`) so sibling fork/exec activity cannot transiently retain another fixture's closed file-lock descriptor. This does not disable explicit worker/writer-contention/process-crash concurrency within tests; the four runtime CI jobs remain parallel.

The Python gates use the standard library; terminal tests discover fresh Cargo artifacts and operate only on disposable fixtures. CI runs all four runtime platforms, exposes optional skip messages, requires non-root permission tests and distinct Linux cross-device fixtures, and rejects tracked-file changes. See [validation methods](docs/validation.md) for maintained coverage, isolation and harness guidance; candidate-specific evidence and remaining release blockers belong in ignored planning notes. Keep distribution ownership separate: the external Homebrew tap owns only its formula and Homebrew checks; this repository owns the independent mise workflow, integration helper and release-binary receipts. Validate each channel in disposable fixtures/runners, never by changing workstation package-manager installations. Neither channel may publish releases, alter existing assets or submit registry entries automatically. Do not equate an earlier commit's CI result with validation of new work. Real ENOSPC/power-loss or mounted-volume fault injection needs a separately approved disposable environment; never fill a workstation disk or automate real-home smoke tests. `scripts/test-cross-device-macos.py` separately requires explicit approval for a fresh 128 MiB HFS+ image and private temporary fixtures; it verifies exact image/device/ownership, runs refusal-only tests and normally detaches. It never uses existing volumes, sudo or disk filling; uncertain attach/failed detach retains the exact scope and stops without force/lazy cleanup. Ordinary macOS tests explicitly skip without its marked fixture; the launcher requires no skips. Its mount-free `--self-test` checks fixture/identity/result guards. `scripts/test-storage-vm.py` is an opt-in launcher restricted to the reviewed `lima-a12` guest with an administrative approval marker, no host shares and a verified 128 MiB ext4 loop image. Its Linux Rust probe is ignored by ordinary tests. Do not create the marker on a workstation, add privileged fault injection to normal CI, enlarge the volume or infer failing-sync/power-loss safety from ENOSPC results.

## Filesystem and recovery invariants

- Never test destructive operations against the real HOME, real dotfiles or package managers.
- Use disposable canonicalized homes/repositories (`tests/support::TestHome`). macOS `/var` aliases are symlinks; use physical temporary paths.
- Do not mutate process-global HOME/XDG variables in tests. Configure isolated child processes instead. CLI tests use deterministic fake Git/missing-Git fixtures and must not require installed external tools. Optional core real-Git integration tests use only disposable repositories and skip explicitly when Git is absent.
- Keep live/state access descriptor-relative and no-follow. Do not substitute ordinary path-based writes for secure helpers.
- Reject unsafe parents, special files, hard links, sensitive ordinary adoption and unsupported template/secret/prerequisite execution. Filename/content heuristics are not proof of secrecy.
- Preserve bounded reads, stable identities and explicit rejection of non-UTF-8 report paths; never silently use lossy path identity.
- Writers require the application lock, explicit approval and fresh independent revalidation. Preview JSON is not execution authorization.
- Persist immutable checksummed intent before live mutations/inverses; verify private durable backups and postconditions. Incomplete/malformed transactions block subsequent writes.
- Keep schema-1 adoption diagnosis/rollback compatible. Schema-2 apply/unmanage uses one recoverable transaction per approved request, immutable source watches and a separate matching removal acknowledgement. No silent format migration.
- Recovery is explicit and guarded. Never automatically replay/rollback on startup or overwrite later user/source edits. Schema-3 bootstrap is separate from schema-1/2 lifecycle journals: private staged Git initialization, durable no-replace publication/registration intents, explicit guarded resume/abandon only. Abandon retains published repositories, registration and private artifacts; never delete a published repository automatically.
- Mutation CLI commands must present previews and collect human-terminal confirmation or explicit --yes. JSON/nonterminal writes never prompt. Link deletion must clearly identify the selected mapping and bind its confirmation internally to that exact ID, without asking the user to type it. --dry-run must not create directories/state/locks/backups/journals or prompt. Keep approvals opaque and bind fresh previews/journal heads under the writer lock.
- TUI approvals must consume the real in-memory core preview, never serialized plans. Use a clear explicit action (key/click) against the reviewed preview for writes, including Adopt all for combined adoption. Removal confirmation must display the exact selected IDs and bind them internally, without typed challenges or redundant confirmation steps. Blocked/dry-run/small layouts cannot approve. Entry --dry-run cannot be toggled off; shrinking clears pending confirmation and removal acknowledgement. Session root selection must remain read-only; only approved bootstrap persists registration/selection. Keep form drafts in memory, accept printable shortcuts as text there, and resolve relative bootstrap paths from a caller-supplied launch directory. q/Ctrl-C during a worker waits for completion; no cooperative write cancellation, detached worker or automatic rollback. Restore the terminal on returns/errors/panics and join active workers before exit. Keep Crossterm input on one thread and progress nonblocking/metadata-only. Test with Ratatui's backend and disposable fixtures; terminal failure/panic injection belongs only in isolated test children.
- Preserve the current same-filesystem atomic-rename constraint; do not add an unsafe cross-device fallback.
- Do not put file contents, local variable values or secrets in ordinary reports, logs or checkpoint metadata. Discover may automatically disclose only its selected eligible regular file through the bounded no-follow core read service (64 KiB; sensitive/binary refusal; no unselected prefetch). Keep this ephemeral payload outside Debug/Serialize, generic metadata models, logs/errors/receipts/history/export; discard on selection/scope/view/shrink/exit and withhold in preview-only/below-floor layouts. Heuristics are not secret-proof; discarding a reference is not secure erasure. Passive reads share the one owned joined worker without blocking navigation or opening activity panels. The separate Git exception remains explicit `git diff --patch`: bounded patch content is disclosed only in that requested report, with unsafe bytes escaped, never in logs/errors/journals. Summary/status reports stay metadata-only; patches are not secret-proof. TUI patch payloads must remain private, outside Debug/Serialize/generic diagnostics/progress/view-model dumps. No prefetch, automatic refresh, clipboard/export or retained patch history; dismissal/scope change/shrink/exit drops the reference, not a guarantee of secure memory erasure. Disclosure confirmation is disabled below 48×14 and is separate from mutation approval. Backups are private but ordinary backups are not encrypted.
- Extend failure-boundary/process-crash tests when changing the executor. Do not claim process-exit tests establish power-loss safety.
- Do not automatically merge Git changes into live-linked sources.
- Git inspection uses a caller-supplied trusted absolute executable, cleared child environment, fixed read-only arguments, no optional locks/index refresh, no hooks/external diff/textconv/fsmonitor/submodule recursion, and bounded concurrent pipe drains/deadlines. Reject configured content filters and partial clones/promisor settings before status/diff; no unsafe fallback, arbitrary arguments, network or writes. This is hardening, not isolation against a malicious same-user config race. Keep Git executable/environment resolution at the CLI boundary.

## Changelog maintenance

git-cliff **2.14.2** is pinned by `scripts/changelog.sh`. Install locally when authorized:

```sh
cargo install git-cliff --version 2.14.2 --locked --root temp/tooling/git-cliff
scripts/changelog.sh
scripts/changelog.sh --check
```

The script uses `cliff.toml`, disables network metadata/command hooks, and changes only the generated file (plus ignored temporary tooling). Its optional `--tag vMAJOR.MINOR.PATCH` labels committed history for release preparation without creating/moving/pushing a Git tag; combine with `--check` before the actual tag exists. It does not install tools, commit, create tags or change releases.

Prefer descriptive Conventional Commit subjects (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`). Legacy non-conventional commits remain included. Release tags follow `vMAJOR.MINOR.PATCH` with optional prereleases.

Generation uses committed history, not the working tree. Regenerate after authorized feature/fix/documentation commits or before release preparation. If committing only the regenerated file, use `chore(changelog): regenerate history`; this maintenance subject is excluded to avoid self-referential churn. `chore(release):` commits are also excluded. Never fabricate commits or tag a release merely to populate the file. A full-history checkout (including tags) is required for reproducible generation.

## Release packaging

See [release mechanics](docs/releases.md). Explicit release approval is required. Stable-version CI retains four native archives for 14 days; tag-triggered publication accepts only successful exact-commit CI artifacts, checks all targets/checksums/provenance and populates a draft before publishing. Keep registry publication separately approved and manual; CI source-package checks must never upload or receive registry credentials. Keep binaries experimental and minimum-runtime claims accurate. Do not overwrite releases or move published tags. Packaging guard tests are mount-free and use disposable synthetic archives; native binary version checks use isolated child homes, never real-home write smoke tests.
